Verification Before Completion Instruction / Evidence Protocol

Evidence before assertions

Make “done” provable.

This skill stops unsupported success claims at the moment they are about to be made. It identifies the exact proof a claim needs, runs that proof fresh, reads the complete result, and reports only what the evidence allows.

The verification gate

Five steps between confidence and a claim.

The gate runs immediately before any statement that work is complete, fixed, passing, correct, or ready. Skipping a step means the claim has not been verified.

Identify

Write the precise claim, then choose the command or checklist that directly proves it.

Run

Execute the full verification now, against the current state. Old output and partial checks do not qualify.

Read

Review the complete output, exit code, failure count, skipped checks, warnings, and tested scope.

Match

Ask whether the observed result supports this exact claim—not a nearby or weaker one.

State

If supported, make the claim with its evidence. If not, report the actual status and the gap.

Claim-to-evidence ledger

Choose proof that matches the sentence.

Passing one kind of check never silently proves another. The skill keeps each claim tied to its own evidence source.

Tests pass

Required evidence
Fresh full test output with zero failures.
Does not prove it
A previous run, a passing linter, or “the change is small.”

The build succeeds

Required evidence
The complete build command finishing with exit code 0.
Does not prove it
Clean logs, type hints, or a successful formatting check.

The bug is fixed

Required evidence
A direct reproduction of the original symptom that now passes.
Does not prove it
Code was edited or a related test happened to pass.

Requirements are met

Required evidence
A line-by-line check against the stated requirements.
Does not prove it
A green test suite that does not cover the complete brief.

How to invoke it

Bring a claim, its context, and a way to prove it.

The skill is most useful at the final boundary: before a commit, handoff, pull request, status update, or move to the next task.

Recommended prompt

Keep the requested claim narrow enough to verify directly.

Before I report this task complete, verify the claim that the release build succeeds and all acceptance tests pass. Run the full relevant commands against the current working tree, read all output, and report the claim only if the evidence supports it. Otherwise, state the exact remaining failure.
Claim The exact status you intend to communicate.
Scope The repository, change, requirement list, or original symptom.
Proof route The authoritative command or acceptance procedure, when known.

What you receive

A supported claim—or an honest status report.

When evidence supports the claim

A concise, attributable completion statement

  • The command or checklist that was run
  • The observed exit status and failure count
  • The scope and freshness of the evidence
  • The precise claim that the result supports
When evidence does not support the claim

The actual state, without euphemism

  • The failing, incomplete, or ambiguous result
  • The exact evidence that contradicts the claim
  • Any unverified requirements or skipped checks
  • No “should,” “probably,” or implied success

Where it fits

Use it at the claim boundary—not as a substitute for judgment.

Ideal moments

  • Before saying a bug is fixed or a task is complete
  • Before committing, pushing, opening a PR, or handing off
  • After a delegated agent reports success
  • Before moving from one delivery phase to the next
  • When a regression test needs a verified red-green cycle

Not a replacement for

  • Defining acceptance criteria or deciding product intent
  • Domain-specific security, legal, or production review
  • Tests that do not exist or cannot observe the real requirement
  • Exploratory updates that clearly make no success claim
  • Human approval where the delivery process requires it

Dependencies & limits

The gate is only as strong as the available proof.

What this skill deliberately does not pretend to know

Tools It relies on the project’s real test, build, lint, VCS, or acceptance commands; it does not invent authoritative checks.
Coverage A green command proves only the scope it actually exercises. Untested requirements remain unverified.
Freshness Evidence from an earlier state cannot support a claim about the current working tree or delivery.

Run the proof. Read the result. Then—and only then—sign the claim.
