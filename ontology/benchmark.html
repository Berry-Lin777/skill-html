Known risk

Acceptance gates

The benchmark uses observable gates, not a decorative score.

Functional gate

Expected state must be retrievable

Create and relate fixtures, reconstruct the active graph, then compare query and traversal output with the expected IDs and properties.

Containment gate

Graph paths must stay inside storage

A traversal attempt passes only if the command rejects it, returns a non-zero exit code, and creates no file outside the configured data directory.

Integrity gate

Invalid writes must block automation

Full acceptance requires validation before append and a non-zero exit signal for violations. The current version does not meet this gate.

Key findings

What is verified, and what still needs an operator.

Verified locally

File-backed CRUD, property filtering, directed relation traversal, explicit violation detection, schema parsing with PyYAML, and graph-path containment all produced the expected observable result.

Not a pre-commit guard

The documented “validate before committing” behavior is not implemented by mutation commands. Treat validation as a separate report, not as rollback protection.

Exit code is not trustworthy

A zero exit status does not mean the graph passed validation. Human review or explicit output parsing is required in automation.

Append-only means retained history

Logical deletion changes active state but does not erase prior values from the ledger. Do not store secrets or data requiring physical deletion.
