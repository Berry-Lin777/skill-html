Instruction file · evidence-first debugging

Find the cause before you touch the fix.

Systematic Debugging turns a failing test, production bug, build error, performance problem, or integration mystery into a traceable investigation—so the final change addresses the origin, not the visible symptom.

The iron law No fixes without root-cause investigation first.
First deliverable A reproducible failure with preserved evidence
Decision point One explicit hypothesis tested in isolation
Final proof A source-level fix verified against the failure
01

Bring a mystery worth investigating.

Use this skill when

  • A test, build, deployment, integration, or production behavior fails.
  • The issue is intermittent, environment-specific, or hidden behind several components.
  • Previous “obvious” fixes did not work, or time pressure is encouraging guesses.
  • A bad value appears deep in a call stack and its origin is unclear.
  • Flaky tests depend on arbitrary sleeps instead of observable conditions.

Do not use it to

  • Skip investigation and request a patch based only on the visible error.
  • Bundle unrelated cleanup or refactoring into a root-cause fix.
  • Claim certainty when the failure cannot be reproduced or the evidence is incomplete.
  • Replace domain experts, production access, logs, or the project’s own test tooling.
  • Keep stacking fixes after three failed attempts without discussing the architecture.
02

Follow four gates. Never jump ahead.

1 Investigate

Establish what happened and where it diverged.

Read the entire error, reproduce the failure, inspect recent changes, collect data at component boundaries, and trace suspicious values backward to their source.

  • Read stack traces
  • Record exact steps
  • Inspect diffs
  • Instrument boundaries
  • Trace data backward
2 Compare

Find the pattern before changing the code.

Locate a working analogue, read its reference implementation completely, list every difference, and identify the dependencies and assumptions that make it work.

  • Find working examples
  • Read references fully
  • List all differences
  • Map dependencies
3 Test

State one theory and change one variable.

Write a specific “X because Y” hypothesis, design the smallest discriminating test, and use its result to confirm the cause or form a new hypothesis.

  • One hypothesis
  • One variable
  • Minimal test
  • Record the result
4 Implement

Prove the failure, fix its source, then verify.

Create the smallest failing test, implement one focused change, rerun the relevant and surrounding tests, and confirm that the original behavior—not merely an adjacent symptom—is resolved.

  • Failing test first
  • Single source-level fix
  • Regression check
  • Document evidence

Multi-component systems

Interrogate every handoff.

For a chain such as CI → build → signing or client → API → service → database, log what enters and exits each boundary. Run once, locate the first broken transfer, then focus the investigation there.

Boundary record Input value, output value, relevant configuration, environment, timestamp, and execution context.
Trace question Where was this invalid value created, and which caller supplied it?
Exit condition Evidence identifies the failing component and explains why its behavior differs from the working path.
03

Ask with enough context to investigate.

Recommended prompt

“Use Systematic Debugging to investigate this failure before proposing a fix. Reproduce it, preserve the complete error, trace data across component boundaries, compare the broken path with a working example, and state one testable root-cause hypothesis. Do not modify code until the evidence supports that hypothesis.”
Failure evidence

Full error text, stack trace, logs, failing command, expected behavior, and actual behavior.

Reproduction context

Exact steps, frequency, environment, relevant inputs, and whether the failure is deterministic.

Change history

Recent commits, dependency or configuration changes, and known differences between environments.

Access boundaries

State what may be inspected or changed and identify sensitive values that must be redacted from logs.

04

Receive an evidence-backed case file.

Record A Reproduction brief

Exact trigger, environment, expected result, observed result, and consistency notes.

Record B Evidence trail

Relevant errors, boundary observations, data-flow trace, recent changes, and working comparisons.

Record C Tested hypothesis

A specific cause, the smallest test that isolates it, and the observed result.

Record D Fix and verification plan

A failing regression test, one focused change, commands to rerun, and remaining risks or unknowns.

3+

Three failed fixes are an architecture signal.

Stop adding patches. If each attempt exposes new coupling, shared state, or symptoms elsewhere, discuss whether the underlying pattern is sound before attempting another change.

Supporting techniques

The package includes backward root-cause tracing, defense-in-depth validation, condition-based waiting, and a shell utility for locating a polluting test.

Operational limits

The skill guides investigation; it still needs project access, executable tests, trustworthy telemetry, and human judgment for architectural decisions.

Safe evidence

Instrument only what is necessary. Redact credentials and personal data, and remove temporary diagnostic logging after the investigation.
